# IVF Digital Twin → Teable: постоянная локальная база прогнозов

Результаты `/run-analysis` всех клиник копятся в self-hosted Teable — по одной базе на
клинику, плюс локальный вьюер карточек пациенток в стиле итогового HTML-отчёта.
Одна команда: `/teable-sync` (или `run_sync.bat`).

```
Teable   http://127.0.0.1:3000     базы, таблицы, срезы, фильтры
Карточки http://127.0.0.1:8788     выбор пациентки по ФИО/ID и карточка цикла
```

## Клиники

Реестр — единственное место, где перечислены клиники: секция `clinics` в
`teable_config.local.json` (в .gitignore; шаблон — `teable_config.local.json.example`).
`processed_dir` можно задавать относительно корня репозитория.

| Код | Клиника | Папка processed |
|---|---|---|
| `two_line` | Two-Line IVF | `data/processed` |
| `fertimed` | Fertimed | `data/processed/fertimed` |
| `ggrc` | GGRC | `data/processed/ggrc` |
| `skyfert` | Skyfert | `data/processed/skyfert` |

Клиника с годовыми прогонами (PERSONA, `data/processed/persona/<год>/`) задаётся ключом
`year_root` вместо `processed_dir`/`supplemental_dirs`: последний год с `run_manifest.json`
становится основным прогоном, остальные — дополнительными, новый год подхватывается сам.
Ключи `fet_links` / `fet_links_private` подключают таблицу криопереносов (PERSONA:
`scripts/persona_fet_link.py`).

Новая клиника = одна запись в `clinics` с пустым `base_id` + `python teable_bootstrap.py
--all`: база создастся, а её id впишется в конфиг сам. Никаких id в bat-файлах и в
команде `/teable-sync` больше нет.

## Схема базы (9 таблиц)

| Таблица | Что внутри | Источник |
|---|---|---|
| **Runs — Прогоны анализа** | Один запуск = одна запись: сколько пациенток, с исходом, в ревью-листе, флагов OZEMA, ссылка на вьюер. Якорь истории. | метаданные прогона |
| **Cycles — Пациентки / циклы** | Мастер циклов, upsert по ключу `ID#датаOPU` — между прогонами не дублируется. Здесь же `cycle_uid`, эмбриолог/врач, метод, исход, кластер, **ссылка «Карточка»** и счётчик «Прогонов». | `OPU_table_enriched.xlsx` + `dt_predictions.csv` |
| **Predictions — Прогнозы моделей** | Все выходы моделей на цикл на прогон: медианы воронки, PRAI (TabPFN) с разбросом членов ансамбля и диапазоном по неизвестным стадиям воронки (поля «PRAI CI низ/верх», «Ширина CI» — историческое имя, это не ДИ), DIGITAL TWIN, MC per transfer / overall / cum, Bayes с ДИ, KAT, NVSA, CSDI, GNN, DNN, кластер и его вероятности, P viable / cancel, OHSS, P без бластоцист, banking. | `dt_predictions.csv`, `tabpfn_predictions.csv` |
| **Prediction vs Reality — Прогноз vs Факт** | Воронка прогноз/факт с флагами ±30%, KAT−PRAI, исход, приоритет ревью. | расчёт по тем же файлам |
| **Regression QC — TabPFN-3 воронка** | Количественный прогноз стадий MII / 2PN / Бласт / Хор.бласт / Витрифицировано: факт, P10, P50, P90 и попадание в интервал; «Стадий вне интервала». | `regression_qc.csv` |
| **Review — Ревью-лист** | Приоритет, основание, ширина CI TabPFN, ссылка на карточку. | `review_list.csv` |
| **OZEMA — Арест-паттерны цикла** | Флаг цикла и результаты OMA / FF / ZA / EEA, число флагов у пациентки, кандидат на обсуждение генетического консультирования, примечание. | `ozema_cycles.csv`, `ozema_genetic_counseling_candidates.csv` |
| **Calibration — Калибровка моделей** | На прогон × модель: Brier, AUC-ROC, Acc@0.5, Mean pred, Real rate, N. | расчёт (нужен scikit-learn) |
| **Files — Файлы прогонов** | Сами CSV/XLSX как вложения, привязанные к прогону. | все файлы из `processed` |

`teable_schema.py` — единственное описание схемы; `teable_bootstrap.py` применяет его
идемпотентно: недостающие таблицы создаёт, недостающие поля добавляет, ничего не
переименовывает и не удаляет.

## Вкладки для работы (views)

Основное рабочее место внутри Teable — вкладка **🔎 Поиск пациенток** на таблице
`Cycles`. Её стоит закрепить: это поиск по всей базе клиники (встроенный поиск Teable
ищет по всем видимым колонкам — ФИО, ID, `cycle_uid`, эмбриолог, врач), а колонки
подобраны так, чтобы решение принималось прямо в строке, без перехода в связанные
таблицы:

`ID пациента · Имя · Дата OPU · Возраст · AMH · Исход · PRAI (посл.) ·
DIGITAL TWIN (посл.) · Приоритет ревью · Флаг OZEMA · OCC · 2pN · Bl · Good Bl ·
Кластер · Карточка · Эмбриолог · Врач · Дата ET · Прогонов · cycle_uid`

Колонки с пометкой «(посл.)» и приоритет/флаг — снимок последнего прогона,
денормализованный на карточку цикла именно ради этой вкладки. Клик по «Карточка»
открывает полную карточку во вьюере, а в самой карточке есть обратная ссылка
«открыть запись в Teable» — заходить можно с любой стороны.

Остальные вкладки создаются там же и работают как готовые срезы:

| Вкладка | Таблица | Что показывает |
|---|---|---|
| ⚠️ Ревью: приоритет 1–2 | Cycles | циклы из ревью-листа, сначала критичные |
| 🧬 OZEMA: флаги | Cycles | циклы с арест-паттерном |
| ❔ Без известного исхода | Cycles | перенос был, исход ещё не внесён |
| 📈 Широкий CI TabPFN | Cycles | диапазон по неизвестным стадиям воронки > 20 пп — часть этапов не внесена (имя вкладки историческое, это не ДИ) |
| 🕓 История прогнозов | Predictions | все прогнозы по всем прогонам, свежие сверху |
| ⚠️ Приоритет 1 | Review | только критичные записи ревью-листа |

### Одинаковый интерфейс во всех клиниках

База, которая росла по частям (таблицы и поля дописывались позже), выглядит иначе, чем
созданная с нуля: таблицы в другом порядке, новые поля в конце каждого представления,
таблица под старым названием. Поэтому `teable_bootstrap.py` при каждом прогоне приводит
все базы к одному эталону — схеме:

* названия и порядок таблиц;
* порядок вкладок внутри таблицы;
* названия полей-обратных связей (Teable даёт им имя таблицы на момент создания);
* порядок и видимость колонок в каждом представлении.

Что при этом **не** трогается: фильтры и сортировки представлений, данные, а также ваше
собственное «скрыть/показать» для полей, объявленных в схеме. Служебные вкладки (те, что
задают свой набор колонок) приводятся к эталонному виду целиком — если нужно поменять
набор или порядок колонок в «🔎 Поиск пациенток», правьте `_SEARCH_COLUMNS` в
`teable_schema.py`, иначе следующий прогон вернёт эталон.

Поля, которых нет в схеме (устаревшие от прежних версий, добавленные вручную), **скрываются
во всех представлениях, но не удаляются** — данные остаются в таблице. Чтобы поле всегда
показывалось, объявите его в `teable_schema.py`.

## Карточки пациенток (вьюер)

`cards_build.py` собирает по одной самодостаточной HTML-странице на клинику из файлов
`processed` и отдаёт их nginx-контейнером на `127.0.0.1:8788` (порт намеренно только на
loopback — на страницах есть ФИО). Вёрстка, типографика и компоненты повторяют
`src/embryo/report.py`, а палитра — своя, **нежно-оливковая** (запрос владельца,
2026-07-28): токены `--accent`, `--hero-a/b` и фоновые цвета в блоке `:root` функции
`_css()` там же, светлая и тёмная темы. Статусные цвета (красный / жёлтый / зелёный)
намеренно оставлены насыщенными — оливковый акцент держит навигацию и шкалы, но не
должен съедать сигнал «в норме / вне нормы». Палитра итогового отчёта `report.py` при
этом не менялась: она закреплена в CLAUDE.md отдельным решением.

Что на странице:

* поиск по **ФИО, ID или `cycle_uid`** и список циклов слева;
* карточка выбранного цикла: вероятность беременности (PRAI с разбросом ансамбля TabPFN + все модели
  рядом, без взаимного ранжирования), воронка «факт → медиана DT → ±30% → P10–P90
  TabPFN-3 → попадание в интервал», риски и структура цикла (кластер, OHSS, отмена,
  banking), вердикт ревью-листа, OZEMA;
* **место цикла в когорте клиники** — перцентиль и медиана по PRAI, DT, ООК, 2PN,
  бластоцистам, хорошим бластоцистам, возрасту, AMH;
* **прослеживание**: история прогнозов этого цикла по всем прогонам (читается из Teable)
  и другие попытки той же пациентки.

Прямые ссылки: `http://127.0.0.1:8788/<код клиники>.html#uid=<cycle_uid>` — ровно такая
ссылка лежит в поле «Карточка» каждой записи Cycles и Review, так что из строки в Teable
открывается карточка именно этого цикла. Поддерживаются также `#id=<ID>` и `#q=<ФИО>`.

### Страница накопительная, а не снимок последнего прогона

`data/processed/<клиника>/` — папка на клинику, а не на прогон, поэтому каждый запуск
перезаписывает в ней `dt_predictions.csv`. Пока карточки строились только из этого файла,
вьюер показывал ровно последнюю выгрузку: прогон Fertimed за июнь (34 цикла, 31.07.2026)
сменил шестимесячный (250), и полугодовые карточки исчезли со страницы — хотя в базе
Teable лежали все 282 цикла. То же было у всех клиник: Two-Line показывал 22 из 78,
GGRC 412 из 502, Skyfert 163 из 579.

Теперь циклы, которых нет в текущем прогоне, восстанавливаются **из самой базы**
(`fetch_archive`): `Cycles` даёт личность, демографию и фактическую воронку,
`Predictions` — все модели, медианы DT, кластер и риски, `Regression QC` — P10/P50/P90
по стадиям, `Review` и `OZEMA` — свои вердикты. Берётся самый поздний прогон каждого
цикла. Карточка из прогона всегда в приоритете: она собрана из файлов, а не из
денормализованного снимка.

Восстановленные циклы помечены значком **«архив»** в списке и врезкой в карточке с
идентификатором прогона, из которого взяты числа. Счётчик над списком называет состав
явно («N из прогона + M из базы»), иначе рост числа циклов после прогона на подвыборке
читался бы как «выгрузка выросла». Поля, которых база не хранит (источник спермы,
отдельный выход TabPFN), в архивной карточке пусты — это отсутствие в архиве, а не в
цикле.

Без доступной базы (`--no-history`, контейнер не поднят) страница строится только по
текущему прогону, как раньше.

### Циклы вне когорты отчёта (`off_cohort`)

Основной прогон отдаёт моделям только переносы с известным исходом, поэтому остальные
циклы OPU-таблицы (freeze-all, отмена переноса, остановка развития, перенос без
внесённого исхода) лежали в `Cycles` одной фактической воронкой, а их карточки были
«архивом» без единого прогноза. `scripts/run_off_cohort.py` считает для них модели
отдельным прогоном в `<processed_dir>/off_cohort/` (файлы основного прогона не
трогаются; KPI, калибровка, review-list и agent packet этот слой не читают).

Уровень моделей — по лабораторным данным цикла (владелец, 2026-09-15):

| Уровень | Условие | Что считается |
|---|---|---|
| full | 2PN > 0 | DT 7.1, TabPFN PRAI, TabPFN-3, DNN; без переноса — оценка для гипотетического переноса (во вход DNN пустое ET = 0, флаг `et_zero_for_dnn`) |
| funnel | OCC > 0, 2PN = 0 | только воронка DT (точка retrieval), вероятность не выдаётся |
| none | OCC = 0 или нет данных | модели не применяются |

Папка `off_cohort` подхватывается синхронизацией сама (или явно — `supplemental_dirs`
в записи клиники реестра): она заливается в ту же базу **отдельным прогоном**
(`<код>-off_cohort-…`, пометка в «Заметках»), а в `Cycles` заполняется поле
**«Охват прогноза»** («Без переноса: …», «Ооциты не получены…»; у когорты отчёта —
«Когорта отчёта»). Циклы без модельного результата не получают пустых строк в
`Predictions`/`Prediction vs Reality` и не засчитывают прогон в «Прогонов».
В карточке такие циклы — свежие (не «архив»), со значком **«вне отчёта»** и врезкой
об охвате; в блоке «Место цикла в когорте» вероятности сравниваются только внутри
когорты отчёта.

```bat
python scripts/run_off_cohort.py "data/inbox/OPU table.xlsx" --dt-check
python scripts/run_off_cohort.py "data/inbox/OPU table.xlsx"
python teable/teable_sync.py --clinic two_line
```

Слой определяется относительно `dt_predictions.csv` последнего основного прогона:
после нового `/run-analysis` его нужно пересчитать, иначе цикл, вошедший в отчёт,
останется и в `off_cohort` (карточка всё равно берётся из основного прогона).

## Запуск

```bat
REM всё сразу (схема + все клиники + карточки)
run_sync.bat                       REM интерактивно
sync_all_clinics.bat               REM в лог, для Планировщика заданий

REM вручную
python teable_bootstrap.py --all
python teable_sync.py --all
python teable_sync.py --clinic ggrc --dry-run
python teable_sync.py --all --cycles-only    REM дозаполнить Cycles без нового прогона
python cards_build.py --all --no-history
```

`--cycles-only` нужен после добавления новых полей в `Cycles`: обновляет мастер циклов и
снимок последнего прогона, но не создаёт запись в `Runs` и не трогает остальные таблицы.

Контейнеры (Teable + карточки): `cd self-hosted && docker compose up -d`.

## Идемпотентность

* Прогон помечается **хешем содержимого** `dt_predictions.csv`; повторная синхронизация
  тех же файлов печатает `[skip]` и ничего не дублирует. Нужно всё равно залить —
  `--force`.
* **Cycles** обновляются по ключу цикла: одна запись на цикл навсегда, история копится в
  Predictions / PvR / Regression QC / Review / OZEMA по разным прогонам.
* Одна упавшая клиника не останавливает остальные.

## Историческая заметка

Облачный спейс на `app.teable.ai` (free-план) имел лимит 1000 строк на весь спейс, и
синхронизация падала на середине с `402 Payment Required`. С 2026-07-21 всё работает в
self-hosted Teable (`teable/self-hosted/docker-compose.yaml`, образ
`ghcr.io/teableio/teable`), без лимита строк. Старый `teable_config.json` (облако)
оставлен как есть.

## Приватность

Teable и вьюер подняты локально, наружу ничего не уходит. Страницы карточек лежат в
`data/processed/_viewer` — внутри gitignored-дерева `data/processed`, как и остальной
локальный слой с ФИО. Это не agent packet: агентам по-прежнему отдаются только
`data/processed/agent_packets/`.
