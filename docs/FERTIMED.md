# Fertimed — правила ingest/normalize (выгрузка МИС 1С)

Согласовано с владельцем 2026-07-18 по факту разбора реальной выгрузки за май
2026 (77 колонок, 145 строк, 1 лист). Этот файл — источник истины по *почему*;
код — в `src/embryo/clinics/fertimed.py` и `config/clinics/fertimed/columns.yaml`.
Архитектура: общий `run_analysis.py`/`kpi.py`/`report.py`/роли-агенты не
меняются под Fertimed — вся специфика живёт в clinic-adapter слое (см. решение
ниже, «Один проект vs новый проект»).

## Один проект vs новый проект

Решение: **один проект**, `config/clinics/fertimed/` + `src/embryo/clinics/fertimed.py`,
а не отдельный репозиторий. Обоснование: почти вся специфика Fertimed
(multi-flag фильтр когорты, fallback-значения, приоритет ролей, кодирование
исхода, другой ПГТ-вендор) концентрируется именно в ingest/normalize-слое —
ровно там, где и предполагался адаптер. `kpi.py` (Wilson CI, Σnum/Σdenom,
Vienna-контроль), `report.py`, контракты, `privacy.py`, роли-агентов и паттерн
внешнего запуска DT/TabPFN/DNN общие и не тронуты. Fertimed получает
собственный `config/clinics/fertimed/columns.yaml` (независимый файл, не
расширяет `config/columns.yaml` клиники A) и собственный
`src/embryo/clinics/fertimed.py`, на выходе дающий ту же каноническую форму,
что `normalize.normalize()` даёт для клиники A.

## Схема выгрузки: что не мапится вообще

Не участвует в анализе (владелец подтвердил явно, 2026-07-18):

- `Внематочная`, `Количество плодных яиц`, `Роды Да/Нет`, `Срок родов`,
  `Метод родоразрешения`, `Количество детей`, `Комментарий по исходу
  беременности` — цель отчёта: клиническая беременность, не роды/осложнения.
- `ФИО Сурмамы`, `Партнёр` — PHI второго/третьего лица в той же строке, не нужны отчёту.
- `Fresh OD`/`fresh OD (код донора)`, `Vitrified OD`/`vitrified OD (код донора)`,
  `ДС`/`ДС (код донора)`, `ДЭ`/`ДЭ (Код донора)` — донорские флаги/коды, игнорируются.
- `SMF` (тяжёлый мужской фактор) — поле заполняется недостоверно, не учитывается.
- `FET`, `PGT-TVP` — не используются как фильтрующие флаги.
- ~~`КАФ`~~ — см. «Клинический контекст» ниже: в майской выгрузке колонка
  содержала билинговые суммы, в исправленной июньской — реальный антральный
  счёт, и с 2026-07-31 она используется, но только как описательный признак.
- Суффиксы номера карты (`-Б`, `-Б/А`, `-М/Б`) — обозначение источника
  средств/составляющая кода, не имеют аналитического значения, не парсятся.

Всё перечисленное активно выбрасывается в `fertimed.py::_DROP_RAW_COLUMNS`
сразу после резолва колонок (не просто "не мапится" — явно удаляется из
кадра, чтобы не разрастаться по локальным файлам без необходимости).

Сопоставление имён в этом списке — **не побуквенное** (`_normalise_header`:
регистр, пробелы и «ё»/«е» игнорируются). До 2026-07-31 сравнение шло строкой
в строку, и две PHI-колонки второго/третьего лица не удалялись ни разу: в
списке стояли `ФИО Сурмамы` и `Партнёр`, а выгрузки называют их `ФИОСурмамы`
(шестимесячная), `ФИО сурмамы` (июньская) и `Партнер` (обе). В агентский пакет
они не попадали никогда — там свой allow-list и `privacy._assert_agent_safe`, —
но в локальных processed-файлах оставались.

## Клинический контекст цикла (описательный слой)

Владелец (2026-07-31) включил в итоговую интерпретацию клинические признаки,
появившиеся в исправленной июньской выгрузке 1С. Слой **мапится, но не
участвует ни в фильтрации когорты, ни в расчёте KPI, ни во входе
DT/TabPFN/DNN** — это описательный контекст для интерпретации (аналог того, как
MIRI/лоты в клинике A: confounder-контекст, не метрика).

| Колонка 1С | Каноническое имя | Заполненность (июнь, когорта отчёта n=34) |
|---|---|---|
| `Тип протокола` | `stim_protocol_type` | 34/34 |
| `Суммарная доза ФСГ` | `stim_fsh_dose` | 28/34 |
| `Триггер` | `stim_trigger` | **1/34** |
| `Начало протокола, день мц` | `stim_protocol_start_day` | 30/34 |
| `Начало стимуляции, день мц` | `stim_stimulation_start_day` | **1/34** |
| `Длительность стимуляции` | `stim_duration_days` | **2/34** |
| `Пункция на день МЦ` | `clin_opu_cycle_day` | 34/34 |
| `КАФ` | `clin_afc` | 29/34 |
| `ФСГ` (базальный) | `clin_fsh_basal` | 11/34 |
| `Дата начала` | `clin_cycle_start_date` | 34/34 (см. ниже) |
| `Дата последней менструации` | `clin_lmp_date` | 34/34 |
| `Диагноз основной` | `clin_dx_primary` | 34/34 |
| `Диагноз сопуствующий` | `clin_dx_secondary` | частично |
| `Причина завершения программы ВРТ` | `clin_termination_reason` | 101/105 по всей выгрузке |

`Осложнения программы ВРТ` не мапится: в июньской выгрузке заполнено 0 строк
из 105.

**Причина завершения читается по ДВУМ популяциям.** В когорте отчёта
(`transferred>0` и известный исход) она по определению почти всегда «Перенос
эмбрионов» — это следствие фильтра когорты, а не наблюдение. Содержательные
значения — «Остановка развития эмбрионов», «Отсутствие оплодотворения»,
«Аномальное оплодотворение», «Овуляция», «Отсутствие пригодных к оплодотворению
ооцитов» — встречаются в циклах, до переноса не дошедших. Поэтому
`clinical.build_lab_population_summary` считает отдельный блок
`cohort.clinical_context.lab_population_termination` по ШИРОКОЙ lab-популяции с
собственным явно названным знаменателем. Складывать или сравнивать его проценты
с процентами когорты отчёта запрещено — это разные популяции.

Сборка — `src/embryo/clinical.py` (по-цикловый `clinical_context.csv` +
когортная сводка `cohort.clinical_context` в агентском пакете), интерпретация —
роль `clinical-context-analyst` → `lead-analyst`.

**Граница моделей.** Слой живёт под префиксами `clin_`/`stim_`, которых нет ни
в `_OPU_ALIASES`, ни в `_DT_ALIASES` (`scripts/run_analysis.py`), поэтому во
вход нейросетей он попасть не может. В частности `clin_afc` — это НЕ
канонический `afc`: канонический ушёл бы в μ первой стадии ZINB Digital Twin
(коэффициент 0.55) и в `normalize.impute_amh`, а владелец решил пустить КАФ
только в интерпретацию. У Fertimed канонического `afc` нет вовсе.

**КАФ и защита диапазона.** Майская выгрузка давала 84 строки из 145 (58%) со
значениями 270–250344 — билинговые суммы под заголовком «КАФ». Исправленная
июньская даёт физиологичный счёт (max 30, r=0.93 с числом фолликулов).
`fertimed.AFC_PLAUSIBLE_MAX = 60`: значение выше границы гасится в пропуск с
предупреждением, чтобы прежний дефект не смог вернуться молча.

**Диагнозы.** Коды МКБ-10 группируются в укрупнённые клинические классы по
`config/clinics/fertimed/diagnosis_groups.yaml` (сопоставление по длиннейшему
префиксу; код без совпадения → «прочее / вне справочника», что означает
«справочник надо дополнить», а не редкую патологию). Группа — корзина для
описательной статистики, не диагноз; агент обязан называть код рядом с группой.
Один цикл может входить в несколько групп (основной + сопутствующие), поэтому
сумма счётчиков превышает число циклов. В июньской когорте `N97.8` («другие
формы») — 20 записей из 34: содержательного сигнала эта категория почти не несёт.

**«Дата начала» и криоперенос.** У криопереносной строки 1С несёт исходную
`Дата пункции` свежего забора, а `Дата начала` описывает уже текущую программу
переноса — интервал «старт → пункция» выходит отрицательным (медиана −105 дней
на 33 строках из 34 в июньской выгрузке). `clinical.py` гасит отрицательный
интервал в пропуск: считать срок между разными циклами нельзя. `ДПМ → пункция`
остаётся определённым для всех строк — последняя менструация переносится 1С
вместе с датой пункции, обе относятся к одному забору (медиана 13 дней).

**Подневного дозирования в выгрузке нет.** Единственное поле дозы — суммарная;
`stim_fsh_dose_per_day` — производная (сумма ÷ длительность), определена только
там, где известны обе величины, то есть в июньской когорте на 2 циклах из 34.

## Одна строка = один цикл

Связывание строк одного пациента (свежий забор → одна или несколько
последующих криопереносных строк) **не делается этим модулем** — задача МИС/её
инженеров: криоперенос-строка уже должна содержать данные протокола
оплодотворения, перенесённые 1С автоматически. Если 1С это не сделала для
конкретной строки (эмбриологические поля пусты), сработает общий фильтр по
`Число инсеминированных` (см. ниже) и строка просто не попадёт в анализ — это
принятый компромисс, а не ошибка. Пациентка, встретившаяся несколько раз за
месяц, считается как разные циклы/попытки.

## Две когорты одного файла: отчёт и лаборатория

С 2026-07-31 из одной выгрузки строятся **две разные популяции**, и путать их
нельзя:

| | когорта отчёта (`fertimed.prepare`) | широкая lab-популяция (`fertimed.prepare_wide`) |
|---|---|---|
| гейт по исходу переноса | да | **нет** |
| гейт по `Число инсеминированных` | да | нет |
| `Лечение` | allow-list (см. ниже) | всё, кроме `Криоперенос` и `Инсеминация` |
| что питает | вход DT/TabPFN/DNN/TabPFN-3, review-list, реконсилиация по исходу | **все** таблицы Vienna KPI и OZEMA |
| июнь 2026 | 34 строки | 64 строки |

Почему это понадобилось. Лабораторные KPI показывают, что лаборатория сделала с
полученными ооцитами, а не чем кончился перенос, поэтому гейт по исходу для них
неуместен по существу. На июньской выгрузке это было не теоретической, а
разрушительной ошибкой: заполненный `Исход переноса/инсеминации` стоит почти
только у криопереносов (39 из 41), а у свежих ЭКО/ИКСИ/ЭКО+ИКСИ — у 2 строк из
46. В результате «широкая» популяция совпадала с отчётной когортой, 32 из её 34
строк были криопереносами с пустым `Число Bl`, и BlR/TGBDR считались по 1–2
циклам, по одному циклу на эмбриолога, при том что вся настоящая работа
лаборатории лежала в отброшенных 46 строках.

Что исключено из lab-популяции и почему именно это:

* `Криоперенос` — счётчики воронки перенесены 1С из исходного протокола
  оплодотворения. Сам этот протокол теперь присутствует в популяции отдельной
  строкой, поэтому оставить обе означало бы посчитать одну пункцию дважды.
  (Прежнее решение 2026-07-18 «у врача криоперенос не исключать» действовало
  ровно потому, что при гейте по исходу свежей строки в популяции не было; с
  широкой популяцией оно превратилось бы в двойной счёт.)
* `Инсеминация` — ВМИ, другая клиническая модальность.
* `Только пункция` **остаётся** в популяции: пункция состоялась, фолликулы/ОКК/
  MII заполнены (10 строк из 13 в июне), и OCCR/MIIR врача обязаны их считать.
  Из метрик эмбриолога строка уходит отдельно —
  `kpi.embryologist_only_exclusion_mask`, потому что до инсеминации цикл не дошёл
  и наблюдения FR/ClR/BlR/TGBDR в нём нет вовсе.
* `ПГТ на размороженных эмбрионах` остаётся: без инсеминированных и без 2PN эти
  строки не попадают ни в один знаменатель, отдельное исключение им не нужно.

Токены — `config/clinics/fertimed/columns.yaml: lab_population.excluded_treatment_tokens`
и `competency_exclusion.embryologist_only_treatment_tokens`.

## Пустой счётчик у закрытого цикла = наблюдённый 0 (2026-07-31)

Признак закрытия цикла — заполненная `Причина завершения программы ВРТ`
(`clin_termination_reason`): «Остановка развития эмбрионов», «Отсутствие
оплодотворения», «Криоконсервация ооцитов», «Овуляция» и т.п. У такого цикла
пустой счётчик ниже уже известной стадии означает, что до неё не дошли, а не что
данных нет. `fertimed._fill_closed_cycle_zeros` заполняет по цепочке
`2PN → дробление → эмбрионы 5 дня`, `2PN → Bl → Bl хор.кач-ва` (в июне: 2/4/7/9
значений соответственно) и печатает предупреждение — молчаливой подстановки нет.
Пустая причина = цикл ещё в культивировании на момент выгрузки, там пропуск
остаётся пропуском и строку снимает `kpi.competency_exclusion_mask`.

Без этого правила BlR/TGBDR систематически завышены: агрегатор требует непустой
числитель, поэтому цикл с 2PN=5 и пустым Bl выпадал целиком — то есть из
знаменателя уходили ровно те циклы, где бластоцист не получилось (в июне таких
6 с заполненным 2PN).

`2PN` сознательно **не** заполняется нулём: строки с `2PN=0` исключаются
отдельным неподвижным решением владельца (см. ниже), и производить их из
пропусков означало бы менять то решение молча.

Из того же решения следует правка общего `kpi._open_cycle_mask`: пока признаком
«цикл ещё идёт» служило отсутствие значения `Число Bl`, из KPI выпадали и
закрытые циклы с остановкой развития, и каждая строка `Только пункция` (у неё Bl
нет по определению). Теперь при наличии `clin_termination_reason` открытым
считается только цикл с пустой причиной; клиники без этой колонки живут по
прежнему прокси.

## Фильтр когорты ОТЧЁТА (порядок, все условия обязательны)

1. `Исход переноса` не пусто.
2. `Число инсеминированных` не пусто — иначе строка удаляется сразу
   (это единственная строка, где реально проводили оплодотворение).
3. `Лечение` ∈ {`Криоперенос`, `ИКСИ`, `Получение ЯК (реципиент)`, `ЭКО`, `ЭКО + ИКСИ`}.
   Отбрасываются: пустое значение, `Только пункция` (нет ни оплодотворения, ни
   переноса), `Инсеминация` (ВМИ — другая клиническая модальность, не ЭКО/ИКСИ),
   `ПГТ на размороженных эмбрионах` (биопсия, не полноценный цикл в этом смысле).

`Лечение` используется **только** для этого фильтра когорты — метод
оплодотворения (см. ниже) берётся из отдельных флагов, т.к. `Лечение` для этой
цели ненадёжен (подтверждено владельцем).

## Метод оплодотворения

Из флагов `IVF`/`ICSI` (значение `Да`/пусто), не из `Лечение`. Оба флага `Да`
одновременно (сплит-цикл ЭКО+ИКСИ) кодируются отдельной категорией
`IVF+ICSI`, не сворачиваются в одну из двух — 10/145 строк майской выборки
были именно такими.

## Импутация и fallback-значения

| Поле | Правило |
|---|---|
| `Количество фолликулов` | пусто → `= Число ОКК` (врачи часто не вносят) |
| `№ попытки` | пусто → `1` |
| `День переноса` | пусто → `5` |
| `Заморожено эмбрионов` (для аналитики) | `= Заморожено эмбрионов + Заморожено бластоцист` (сумма двух колонок выгрузки; `min_count=1`, чтобы обе-пустые не превращались в фиктивный 0) |
| `АМГ`/АФК для импутации | `Количество фолликулов` как fallback АФК — уже общая логика `normalize.impute_amh`. `КАФ` этой цели НЕ служит и после 2026-07-31: он идёт в описательный `clin_afc`, а не в канонический `afc` (см. «Клинический контекст цикла») |

## MII: два разных потребителя, одно значение — недостаточно

Vienna KPI (MIIR = MII/OCC) обязан использовать **только реально известный**
MII (проектное правило "MII необязателен... MIIR считается только при
известном MII" не меняется под Fertimed). Но нейросети (Digital Twin/TabPFN)
не должны терять ЭКО-циклы только из-за того, что MII для конвенционального
ЭКО обычно не фиксируется (ооциты не денудируются перед инсеминацией так, как
перед ИКСИ). Поэтому:

- Канонический `mii` хранит **только** настоящее значение (`NaN`, если
  неизвестно) → корректно течёт в `kpi.compute_kpi()` (MIIR остаётся раздельным
  для ЭКО/ИКСИ по флагам, как для клиники A).
- Отдельная колонка `mii_ml_fallback` (`fertimed.MII_ML_FALLBACK_COLUMN`) =
  `mii`, если известен, иначе (только для ЭКО-строк) `= Число инсеминированных`.
- `scripts/run_analysis.py` подставляет `mii_ml_fallback` вместо `mii`
  **только** при построении `model_input.xlsx` (вход DT/TabPFN), через
  config-гейт `quirks.model_fallback_columns` в
  `config/clinics/fertimed/settings.yaml` — `kpi_computed.csv`,
  `OPU_table_enriched.xlsx` и лабораторный KPI это не затрагивает.

## Цепочка MII→OCC→фолликулы: только для моделей (2026-07-28)

Тот же приём распространён на `occ` и `follicles`. Выгрузка 1С заполняет их
далеко не всегда: на 6-месячной когорте (250 циклов) настоящий `occ` есть у
101 строки, `follicles` — у 79. Из-за этого DNN (`Evo_calculations.py`)
отбрасывала строку целиком — в её 18 признаках обучения не допускается ни
одного пропуска, а ноль намеренно не подставляется вместо пропуска. Покрытие
DNN составляло 80/250.

- `occ_ml_fallback` = `occ`, если известен, иначе модельный MII
  (`mii_ml_fallback`).
- `follicles_ml_fallback` = `follicles`, если известны, иначе `occ_ml_fallback`.
- Подставляются в канонические колонки **только** для `model_input.xlsx`.
  `run_analysis.py` строит для этого отдельную когорту (`model_cycles`) из того
  же нормализованного фрейма и проверяет, что состав `cycle_uid` совпадает с
  `kpi_cycles` — иначе обратный join разъедется. Покрытие DNN → 206/250.

**Почему нельзя пускать это в KPI.** `OCCR = OCC/фолликулы` и `MIIR = MII/OCC` с
производным знаменателем вырождаются ровно в 1.0. На cleaned-файле (где ту же
цепочку заполняет skill `reformat-1C-report`) это давало `OCCR = 1.0` у 212 из
250 циклов и `MIIR = 1.0` у 215 — то есть таблица KPI врачей, которая по
правилам проекта состоит ровно из OCCR и MIIR, становилась целиком артефактной.
Тот же класс дефекта, что с производной колонкой фолликулов в GGRC.

До 2026-07-28 частный случай этой ошибки жил в самом пайплайне: `prepare()`
писал `follicles ← occ` прямо в канонический `follicles`, из-за чего OCCR давал
1.0 у 63 из 101 цикла. Подстановка перенесена в `follicles_ml_fallback`;
честные значения — `OCCR` n=79, `MIIR` n=41 (медиана 0.800). Знаменатели
маленькие — это свойство выгрузки, а не регресс.

Следствие: **основной пайплайн получает сырую выгрузку**, а не `*_cleaned.xlsx`
из skill'а `reformat-1C-report`. Отдавать cleaned-файл на вход не нужно и
вредно: цепочка уже заполняется внутри пайплайна и только там, где можно, а
сам cleaned вдобавок бинаризует «Исход переноса» в 0/1, чего
`fertimed._classify_outcome` не понимает (прогон падает на
«нет строк одновременно с переносом ET>0 и заполненным исходом»).

## Три роли эмбриолога/врача — приоритет атрибуции

Выгрузка несёт раздельные поля `Эмбриолог на пункции` / `Эмбриолог,
проводивший оплодотворение` / `Эмбриолог на переносе` (в 93 заполненных
строках майской выборки все три совпадали только в 7). Для KPI-атрибуции
важен эмбриолог, **проводивший оплодотворение** (FR/ClR/BlR — следствие
работы с ооцитами/культурой, не пункции/переноса); эта информация чаще всего
теряется при выгрузке из МИС, поэтому приоритет:

1. `Эмбриолог, проводивший оплодотворение`
2. `Эмбриолог на пункции`
3. `Эмбриолог на переносе`

Врач для KPI врача (OCCR/MIIR) — приоритет:

1. `Врач на пункции` (основной врач)
2. `Врач на переносе`

## Кодирование исхода переноса

- `1` — любая клиническая беременность (одноплодная/многоплодная — не важно,
  важен факт наступления). Маркер: подстрока `"+28"` в тексте.
- `0` — `"не наступила"` или `"биохимическая"` (`"Беременность биохимическая"`/
  `"беременность биохимическая"`, регистронезависимо).
- Артефакт выгрузки — одна строка мая содержала три исхода, склеенных через
  `;` (`"...не наступила; ...+28 дней (одноплодная); ...+28 дней
  (многоплодная)"`). Владелец подтвердил: кодировать как `1`, если среди
  склеенных значений есть хоть один положительный маркер — без отдельного
  предупреждения (это ожидаемый, не аварийный случай).
- Текст, не подпадающий ни под один известный маркер, → `NaN` (пропуск) **с
  предупреждением** (`warnings.warn`) — в отличие от композитной строки это
  сигнал, что появился новый, ещё не описанный вариант текста и словарь нужно
  расширить, а не молчаливая догадка.

Это кодирование — собственная функция Fertimed
(`fertimed._classify_outcome`), не общий `normalize.outcome_to_binary()`:
общая функция проверяет негативные маркеры ПЕРЕД позитивными (это специально
для клиники A), что дало бы `0` для композитной строки Fertimed, а владелец
явно попросил `1`. Приоритет разный между клиниками — вот почему это не общий
код.

## Общий фильтр 2PN=0 (клиника A) — тоже применяется к Fertimed

`kpi.py::compute_rates()` жёстко (не через конфиг) исключает строки с `2PN=0`
из KPI/модельного датасета. Так как `kpi.py` общий, это правило автоматически
действует и для Fertimed. Владелец подтвердил (2026-07-18): сохранить то же
исключение, не делать конфигурируемым.

Единственная граница (2026-07-31): та же функция отбрасывала и строки с **пустым**
2PN, что шире заявленного правила — пропуск не есть записанный ноль. Для врачебной
таблицы это снимало каждую строку `Только пункция`, хотя OCCR=ОКК/фолликулы и
MIIR=MII/ОКК считаются выше стадии оплодотворения и там это полное наблюдение.
Поэтому `compute_rates(..., drop_without_two_pn=False)` вызывается ровно для
врачебного кадра. Записанный `2PN=0` по-прежнему исключается в обоих режимах.

В отличие от изначального плана ("своя DNN, своё окружение"), решено
переиспользовать те же внешние инструменты, что и у клиники A:

- **Digital Twin** — та же служба IVF Digital Twin 7.1 через REST API (с 2026-09-13;

  содержит только циклы этой клиники, коллизий между клиниками нет.
- **TabPFN** — тот же batch-адаптер, отдельный выходной файл
  (`data/processed/fertimed/tabpfn_predictions.csv`).
- **DNN-проверка** (`external_tools.dnn_verifier`) — та же модель/окружение

- **TabPFN-3 regression** — тот же скрипт/окружение, `enabled: true`,
  отдельный выходной CSV в `local_private/fertimed/`.

### Покрытие DNN ≠ статус DNN (2026-07-31)

`dnn_status="valid_saved_scaler"` говорит только о том, что модель отработала с
сохранённым scaler, и НЕ означает, что когорта покрыта. `Evo_calculations.py`
отбрасывает строку с пропуском в любом из 18 признаков обучения, а у
криопереносных строк 1С не заполняет `Число Bl` и `Число Bl хор.кач-ва` — в
июньском прогоне прогноз получили **2 цикла из 34**, и колонка DNN в отчёте
выглядела так, будто модель не запускалась. Гейт при этом стоял: `enabled: true`
и в `config/clinics/fertimed/settings.yaml`, и в общем `config/machine.local.yaml`.

Пайплайн теперь считает покрытие явно: поле `dnn_coverage`
(`{"scored": …, "cohort": …}`) в `run_manifest.json` плюс предупреждение в stderr
при неполном покрытии. Само покрытие этим не чинится — это пробел выгрузки 1С
(криоперенос-строка несёт 2PN и дробление, но не Bl), и закрывается он либо на
стороне МИС, либо связыванием криоперенос-строки с исходной пункцией. Заполнять
Bl нулём здесь **нельзя**: бластоцисты в таком цикле были, один из них перенесли.

## Парсер ПГТ-А под Fertimed (реализован 2026-07-19)

Личный кабинет генетической лаборатории Fertimed:
`https://my.f-genetics.com/#/cases/orders` (подтверждено владельцем
2026-07-18). Другой вендор, PDF-отчёт менее подробный, чем eMap Cycle Report
клиники A (нет CNV QC noise/analysis settings — только euploid/aneuploid/
mosaic + рекомендация по переносу). Парсер `src/embryo/clinics/
fertimed_pgt.py`, `pgt.enabled: true` в `config/clinics/fertimed/
settings.yaml`. Скачивание отчётов остаётся ручным/интерактивным шагом
(claude-in-chrome, по аналогии с шагом 2b клиники A в
`.claude/skills/run-analysis/SKILL.md`) — сам парсер уже сопоставляет PDF из
`pgt.reports_dir` с `cycle_uid` и считает когортные признаки. `PGT-ET`=`Да` в
выгрузке — сигнал к тому, что ответ нужно искать в этом кабинете. `PGT-TVP`
не используется даже как сигнал.

### Механика скачивания через claude-in-chrome (отработано 2026-07-19)

Вход на этом ПК автоматический (как и у `pa.ivf.uz` клиники A). Собери
worklist локально (ФИО + Date OPU/ET пациентов с известным флагом заказа —
`PGT-ET`/`pgt_et_flag`=`Да` — у которых ещё нет файла в `pgt.reports_dir`),
затем на каждого:

1. Открой `https://my.f-genetics.com/#/cases/orders`. **Перед каждым новым
   поиском обязательно закрой любое открытое PDF-превью (крестик в его
   тулбаре)** — оно переживает клиентский роутинг SPA и следующий клик/ввод в
   поиск может незаметно попасть в невидимый повторно открывшийся оверлей,
   из-за чего результаты поиска молча не обновятся (страница будет выглядеть
   как предыдущий запрос).
2. Клик в поле «Поиск» (правый верхний угол) → ввести фамилию (короткую,
   без имени — полное "Фамилия Имя" иногда не матчится) → подождать ~2–3 с
   (поиск живой, с debounce, Enter не обязателен).
3. Прочитать текст страницы (список карточек: № заявки/«СОЗДАНИЕ», № кейса/
   «КЕЙС», ФИО, `Анализ: T1, T2...`, статус — `Выдан`=готово, `В работе`,
   `FG ожидает образцы`=ждём материал, — и дата выдачи).
4. **Критерий совпадения с нужным циклом**: дата выдачи отчёта должна быть
   примерно на 2–4 недели ПОЗЖЕ `Date OPU` этого цикла (биопсия происходит на
   5–6 сутки после пункции, отчёт — ещё через 2–3 недели). Если у пациентки
   есть только более старые «Выдан»-кейсы, датированные РАНЬШЕ нужного OPU —
   отчёта для этого конкретного цикла ещё нет, пропустить (не скачивать
   чужой/старый цикл). Если результатов вообще нет («К отправке ничего
   нет» без кейсов) — для этого ФИО в кабинете ничего не заводили.
5. При совпадении: перейти напрямую на `.../#/cases/<ID кейса>/documents`
   (быстрее, чем кликать по строке) → карточка «Результат» → «Скачать или
   распечатать» → в открывшемся превью нажать «Загрузить» (просто открыть
   превью не сохраняет файл на диск).
6. Файл падает в `~/Downloads/<ФИО>-PGT<id>-<timestamp>.pdf` — перенести в
   `pgt.reports_dir` (`data/processed/fertimed/local_private/pgt_reports/`,
   не коммитится). Имя файла не важно — `fertimed_pgt.analyze_reports`
   сопоставляет по Subject ID + окну `Date OPU..Date ET` внутри самого PDF.

На практике (первый прогон, ~15 пациентов проверено) совпадение находится
примерно в 1 из 3–4 случаев: для многих цикл ещё физически не успел получить
результат (OPU за 2–8 недель до текущей даты при обычном сроке обработки
2–4 недели — граница может не наступить к моменту запуска), это нормально,
не повод считать шаг сломанным.

## Остальные открытые задачи (не блокируют текущий адаптер)

- **MIRI/лоты расходников** — у Fertimed нет ни логов инкубатора, ни выгрузки
  Airtable по лотам. `miri_logs.enabled: false`, `consumable_lots.enabled:
  false` — оба шага гейтятся конфигом и полностью пропускаются, без ошибок.
- **AMH/BMI импутация** — унаследована от клиники A (age+AFC(→follicles)+OCC)
  как отправная точка; Fertimed не запрашивала свою формулу. Пересмотреть
  отдельно, если понадобится другая калибровка для этой популяции.
- **Контракт признаков DT** (`selected_features` в settings.yaml) — тот же
  список, что у клиники A; все поля выводимы из канонической формы Fertimed
  тоже. Подтвердить отдельно, если/когда для Fertimed будет обучена
  собственная версия ансамбля Digital Twin.
