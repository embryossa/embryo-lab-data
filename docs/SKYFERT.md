# Skyfert

Первая версия (согласована с владельцем 2026-07-21, утро) держала Skyfert вне
`scripts/run_analysis.py`/`--clinic` — только отдельный KPI/OZEMA-тест
(`scripts/skyfert_kpi_test.py`). Позже в тот же день владелец подтвердил
полный прогон (Digital Twin, TabPFN, реконсиляция, HTML-отчёт) — тот же
уровень, что у Fertimed. Из двух вариантов (новый отдельный оркестратор
vs. расширение `run_analysis.py --clinic`) владелец выбрал **расширение
`run_analysis.py --clinic skyfert`**, переиспользуя уже отлаженный оркестратор
(как это уже сделано для Fertimed), а не поддерживать второй с нуля. Секция
"Полный прогон" ниже — актуальный способ; `scripts/skyfert_kpi_test.py`
остаётся как самостоятельный быстрый KPI/OZEMA-смоук-тест (не требует внешних
DT/TabPFN, не строит HTML).

Код: `src/embryo/clinics/skyfert.py` (используется обоими путями — и
`scripts/skyfert_kpi_test.py`, и `--clinic skyfert`) + сам
`scripts/skyfert_kpi_test.py`, конфиг: `config/clinics/skyfert/`. Как и у
Fertimed, `src/embryo/clinics/fertimed.py` не используется и не изменялся ни
в каком виде — общие с остальным проектом только *генерические* модули
(`ingest.py`, `normalize.py`, `kpi.py`, `ozema.py`, `privacy.py`, `_io.py`,
`dt_api.py`, `tabpfn_runner.py`, `reconcile.py`, `analytics.py`,
`report.py`, `contracts.py`), не содержащие кода, специфичного ни для
Fertimed, ни для клиники A.

## Источник данных

`SkyFert.xlsx`, один лист (`Sheet1`), один заголовок (не требует специального
парсинга в отличие от первой присланной версии — "отчет по клеткам 2025.xlsx"
с 2-строчным объединённым заголовком и строкой "В ИТОГЕ", которая была
заменена владельцем на эту чистую версию). 579 строк = 579 циклов/попыток
(один ряд — один цикл, тот же принцип, что у Fertimed).

## Упрощённый охват (не меняется полным прогоном)

Нет и не будет: MIRI/логов инкубатора, лотов расходников (Airtable), ПГТ-А,
разбивки KPI по эмбриологу/врачу, дат (`Дата пункции`/`Дата переноса`), ФИО,
MII. `config/clinics/skyfert/columns.yaml` резолвит только 16 колонок, реально
присутствующих в выгрузке. Соответствующие вкладки HTML-отчёта (KPI
эмбриологов, KPI врачей, MIRI, Партии расходников, PGT) для Skyfert
показывают "нет данных" — это штатное поведение `report.py`, тот же механизм,
которым уже пользуется Fertimed для своих отсутствующих MIRI/лотов, не новый
код. Вкладка KPI эмбриологов/врачей пуста потому, что в выгрузке физически
нет колонок эмбриолог/врач (`kpi.aggregate_kpi_slices`/
`analytics._lab_kpi_slices` просто не создают эти ключи, если колонки нет —
без ошибки).

## Полный прогон (владелец подтвердил 2026-07-21, вечер)

Запуск: `python scripts/run_analysis.py "C:\Users\User\Desktop\IVF\SkyFert\SkyFert.xlsx" --clinic skyfert`.
Даёт то же самое, что и `--clinic fertimed`: Digital Twin, TabPFN, реконсиляция
(`dt_predictions.csv`, `OPU_table_enriched.xlsx`), полный лабораторный KPI
(overall + срез по методу IVF/ICSI — без среза по времени, дат нет), OZEMA,
вкладочный HTML-отчёт, пакет для агентских ролей Claude.

Изменения в `scripts/run_analysis.py` для этого — три точечных,
клинико-зависимых правки (не трогают поведение клиники A/Fertimed):
`_CLINIC_NORMALIZERS["skyfert"] = skyfert.prepare`; в `_add_opu_aliases` —
ветка `clinic == "skyfert"` **перед** общей ID+Date OPU веткой (иначе Skyfert
без дат провалился бы в `elif "ID" in out.columns: out["_key"] = out["ID"]` —
неверно, т.к. ЭМК повторяется у разных физических пациенток, см. ниже); в
`main()` — строка `if args.clinic == "skyfert": kpi_cycles["Patient Full Name"]
= kpi_cycles["patient_id"]` (см. "ФИО-placeholder" ниже).

### ФИО-placeholder = ЭМК

Внешний Digital Twin (`dt_postprocess.py`) целиком пропускает строку с пустым
`ФИО` (`if fio.lower() in ("итого", "") or not fio: skip`). В выгрузке Skyfert
колонки ФИО нет вообще. **Решение владельца (2026-07-21): использовать ЭМК
(номер карты) как заполнитель ФИО** — клиника и так передала данные уже
деидентифицированными до уровня "только ЭМК", так что новой утечки PHI это не
добавляет. Строка выше в `main()` использует общий механизм алиасов
`_DT_ALIASES["Patient Full Name"] = "ФИО"` — отдельной функции не потребовалось.

### Когорта прогона

DT/TabPFN запускаются на том же множестве, что и для любой другой клиники —
`transferred>0 & Preg.notna()` (`_eligible_cycles` в `run_analysis.py`, ничего
Skyfert-специфичного здесь нет). Владелец подтвердил (2026-07-21): "прогон
делаем для циклов где известен исход" — совпадает с уже существующим
поведением.

### DNN и TabPFN-3 regression выключены по умолчанию для первого прогона

`config/clinics/skyfert/settings.yaml`: `external_tools.dnn_verifier.enabled:
false`, `external_tools.tabpfn_regression.enabled: false`. EVO (DNN) обучена/
откалибрована на данных клиники A/Fertimed — поведение на совсем другом
профиле данных Skyfert (MII всегда неизвестен, нет дат) не проверялось.
TabPFN-3 regression сравнивает факт против P10–P90 по воронке — с учётом уже
известной проблемы качества выгрузки (`cleavage_d3 > two_pn`, см. ниже) это
сравнение было бы зашумлено с самого начала. Включить любое из двух —
`enabled: true` в settings.yaml, разовая правка.

### Исправленный баг: build_cycle_key и позиционный ключ

`_add_opu_aliases(..., clinic="skyfert")` вызывается в `run_analysis.py`
дважды на разных срезах одного и того же `normalized` — на полной
lab-популяции (`lab_cycles`, для OZEMA) и на eligible-подмножестве
(`kpi_cycles`, для KPI/DT/TabPFN). Старая версия `build_cycle_key`
использовала позиционный `np.arange(1, len(df)+1)`, пересчитываемый заново на
каждом срезе — один и тот же физический цикл получал РАЗНЫЙ `_key`/`cycle_uid`
в зависимости от того, на каком срезе функция была вызвана, что ломало бы
сверку OZEMA против KPI/review-list. Исправлено (2026-07-21): ключ строится
на `df.index`, а не на длине среза — `ingest.load_table` присваивает единый
сквозной `RangeIndex` один раз при загрузке файла, и ни `resolve_columns`, ни
`normalize.normalize`, ни `kpi.compute_kpi` его не сбрасывают, так что один и
тот же ряд исходного файла получает один и тот же `_key` независимо от среза.
Регрессионный тест — `tests/test_skyfert_ingest.py::
test_cycle_key_consistent_across_full_population_and_eligible_subset`.

### Исправленные попутные баги в `report.py` (не специфичны для Skyfert, но проявились только на данных Skyfert)

Обнаружены дозвоночным прогоном полного пайплайна на подмножестве реальных
строк (до этого не проявлялись на клинике A/Fertimed):
- `_build_similarity_graph` падал с `ValueError: Input contains NaN`, если
  колонка признака (`MII`, `afc`) целиком NaN по всей когорте — `.median()`
  такой колонки тоже NaN, `.fillna(median)` — no-op. У Skyfert MII и AFC не
  собираются вообще. Исправлено: колонки без единого известного значения
  отбрасываются до вычисления медианы (с повторной проверкой порога "нужно
  ≥3 признака" — при недостатке тот же путь "недостаточно данных", что и
  раньше).
- `row.get("patient_name") or row.get("Patient Full Name") or "—"` (вкладки
  "Прогноз беременности" и "Review-list") падал с `TypeError: boolean value of
  NA is ambiguous`, если колонка присутствует, но значение в конкретной строке
  — `pd.NA` (не `None`/`np.nan`), например когда ни DT, ни OPU-мастер не
  вернули имя. Исправлено новым хелпером `_first_present()` (pd.NA-safe),
  применён к обеим парам (`patient_name`/`Patient Full Name` и
  `patient_id`/`ID`) в обоих местах.

## "ЭМК" — ненадёжный уникальный ключ пациента

`ЭМК` (номер карты) повторяется у строк с физически несовместимым разбросом
возраста в пределах одной выгрузки (например ЭМК 5822: возраста 34/42/44/—/38/
41/43 на 7 строках) — то есть один и тот же номер карты используется для
разных физических пациенток на разных приёмах (карта переиспользуется), и
здесь нет ни одной колонки даты, чтобы разрешить это обычным способом
(`ID+Date OPU`, как у клиники A/Fertimed). `skyfert.build_cycle_key()` поэтому
хэширует `ЭМК + порядковый номер строки исходного файла` (`df.index`, единый
сквозной `RangeIndex`, назначенный один раз при загрузке — см. "Исправленный
баг" выше) — уникальность гарантирована в пределах одного прогона на одном
файле, но `patient_id` сам по себе (как в crosswalk) не может использоваться
для сопоставления "один и тот же пациент" между разными строками, если
понадобится такая аналитика (например, OZEMA "≥2 флагов у одного пациента" в
этом тестовом скрипте не считается специально по этой причине — потенциально
ненадёжна для Skyfert).

## Кодирование исхода

Тот же словарь `outcome:` (affirmative/negative exact + substrings), что и
`config/columns.yaml` клиники A — текст выгрузки Skyfert использует ровно те
же формулировки ("беременность клиническая" / "беременность не наступила" /
"беременность биохимическая"), собственного словаря писать не потребовалось.

## Известная проблема качества выгрузки: "Число дробящихся на 3 день" > "2 pN"

Обнаружено первым тестовым прогоном (2026-07-21): в eligible-когорте (перенос
>0 и известный исход) значение `cleavage_d3` превышает `two_pn` на 57% строк
(280/495 непустых пар), равно на 41%, меньше — только на 2.2%. Пример из
сырого файла: ЭМК 4547 — `2 pN=1, дробящихся=3, эмбрионов 5 дня=2, Bl=1`.
Средние по всей выгрузке: OCC≈8.35, дробящихся≈6.78, 2 pN≈5.25 — дробящихся
стабильно между OCC и 2 pN, а не подмножество 2 pN, как предполагает формула
Vienna (`ClR = cleavage_d3 / two_pn` в `kpi.py`, общая для всех клиник).

Гипотеза (не подтверждена клиникой): МИС Skyfert считает в "дробящихся на
3 день" ВСЕ дробящиеся ооциты, включая аномальное оплодотворение (1PN/3PN),
не только вышедшие из 2PN-чека — распространённая лабораторная практика,
но несовместимая с денаминатором Vienna ClR/BlR/TGBDR "как есть".

**Решение владельца (2026-07-21): считать как есть, не подменять формулу и
не пытаться угадать корректирующий знаменатель.** Это проблема выгрузки МИС
клиники — повод для разговора с их разработчиками, не задача этого пайплайна.
`scripts/skyfert_kpi_test.py` печатает предупреждение с числом затронутых
циклов при каждом запуске, но не блокирует и не корректирует расчёт. Как
следствие ClR у Skyfert систематически завышен (наблюдалось >100% в первом
прогоне), BlR/TGBDR тоже завышены тем же механизмом (тот же знаменатель
`two_pn`) — интерпретировать эти три метрики для Skyfert с этой оговоркой.

Результаты — та же структура `data/processed/skyfert/`, что и у Fertimed:

и `kpi_computed.csv` — общие имена, полный прогон их перезаписывает своей
(корректной, полной) версией.
